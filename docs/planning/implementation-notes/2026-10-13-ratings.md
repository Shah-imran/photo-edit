# Ratings (0-5 stars)

Related roadmap: Phase A, "Library DAM and workspace chrome" (PDF
sections 8-9, 24) in `docs/planning/PRODUCT_ROADMAP.md` -- the bullet
"**Ratings** and **pick/reject** (or flags); **keywords** on disk or
sidecar (design choice: XMP vs JSON)." This slice builds only the
Ratings half of that bullet. Pick/reject flags and keywords are
explicitly **the next slice**, not this one -- the same deferral
pattern "Import presets" used relative to the Profile-selector slice
(`docs/planning/implementation-notes/2026-10-13-import-export-presets.md`).

This is library-metadata plumbing mirroring an existing, complete
feature in this codebase almost exactly: **Favorite** (a per-image
boolean flag in `LibraryCatalogService`/`LibraryController`/
`FilmstripView`/`MainWindow`). Every layer below was built by reading
the Favorite feature end to end first and following its exact
structure for Ratings.

## 1. Problem, goal, and non-goals

**Problem.** There was no way to assign a quality rating to a library
image. The only existing per-image "importance" signal was the
boolean Favorite flag; there was no graded 0-5 scale.

**Goal.** Add a `rating: int` (0-5) field to `LibraryEntry`, a
`LibraryCatalogService.set_entry_rating()` setter, a
`LibraryController.set_entry_rating()` delegate, a `FilmstripView`
"Set Rating" context-menu submenu emitting `rating_changed`, and the
one-line `MainWindow` wiring connecting the two -- the exact five
layers Favorite already uses, mirrored field-for-field and
method-for-method.

**Non-goals (explicit scope boundary for this slice):**

- **Pick/reject flags are the next slice, not this one.** The roadmap
  bullet covers both; this note and this diff build only the Ratings
  half. A flag (pick/reject/unflagged, a three-state marker distinct
  from a 0-5 rating) is a separate follow-on feature.
- **Keywords are also not this slice** -- the same roadmap bullet
  mentions them too, and they remain an undone Gap.
- **No dedicated "Ratings" filter/collection entry in the library
  sidebar.** Favorites got a dedicated filter mode (`set_filter("favorites")`
  in `FilmstripView`, plus a "Favorites" row with a count badge in
  `LibraryPanel`/`library_view.py`). Ratings gets no equivalent in this
  slice: no new sidebar row, no new `_filter_mode` value, no
  `"rating_count"`-style aggregate in `LibraryController._emit_libraries()`.
  This is a deliberately narrower scope than Favorites' filter
  integration -- a reasonable follow-up (e.g. "4+ stars" filter), but
  it adds sidebar/filter UI surface this slice does not need. A
  rating is surfaced via the filmstrip item's **tooltip only** (see
  Design below).
- **No rating-based sorting.** `FilmstripView` already has a sort
  control (`set_sort("added"|"name")`, the "Sort" toolbutton). Rating
  is not added as a third sort mode in this slice -- a natural future
  extension, not built now.
- **No change to the existing favorite "★" item-text display.** A
  filmstrip item already shows a single "★" character in its `text()`
  when favorited (`item.setText("★" if favorite else "")`); this
  slice does not touch that text or its meaning in any way. Rating
  display goes in the tooltip only, prepended the same way the
  existing `"Favorite\n"` prefix already is, so both pieces of
  information (favorite state and rating) can appear in the same
  tooltip simultaneously without either one overwriting the other.

## 2. Current behavior (before this slice)

`LibraryEntry` had no notion of a rating at all. `FilmstripView`'s
`_apply_entry_payload()` only read `payload.get("favorite", False)` to
build the item's text/tooltip/stored `UserRole` data, and its
`_show_context_menu()` built a single-action menu toggling Favorite.
`LibraryController._entry_payload()`/`_on_thumbnail_ready()` already
included `"favorite": entry.favorite` in both per-entry payload dicts
it builds (used by the filmstrip); neither included anything about a
rating, because there was nothing to include.

## 3. Design

### `LibraryEntry.rating` field and clamping

`rating: int = 0` was added directly alongside `favorite: bool = False`
in the `LibraryEntry` dataclass, threaded through the exact same
`to_dict()`/`from_dict()` methods `favorite` already uses. On read,
`from_dict()` uses a new module-level `_clamp_rating(value) -> int`
helper instead of a bare `int(payload.get("rating", 0))`:

```python
def _clamp_rating(value) -> int:
    try:
        rating = int(value)
    except (TypeError, ValueError):
        return 0
    return max(0, min(5, rating))
```

This defends against three distinct cases a plain cast would not:
a missing key (`payload.get("rating", 0)` already yields `0`, the
same backward-compatible default pattern `favorite`'s own
`payload.get("favorite", False)` establishes -- an older catalog file
written before this slice simply lacks the `"rating"` key and loads
cleanly as `0`), a corrupt/non-numeric persisted value (e.g. a string
that doesn't parse, falls back to `0` rather than raising), and an
out-of-range persisted value (e.g. a hand-edited catalog file with
`"rating": 99` or `"rating": -3`, clamped into `0..5` rather than left
to propagate an invalid value into the UI).

### Clamp vs. raise in `set_entry_rating`

**Decision: clamp, not raise.** `LibraryCatalogService.set_entry_rating(library_id, path, rating)`
reuses the same `_clamp_rating()` helper to coerce its `rating`
argument into `0..5` before comparing/storing, rather than raising
`ValueError` on an out-of-range input. This mirrors
`set_entry_favorite`'s own defensive `favorite = bool(favorite)`
coercion-not-rejection style, and was judged friendlier for a
library-metadata setter: a caller building a "Set Rating" UI (the
`FilmstripView` context-menu submenge built in this slice) only ever
passes one of the six well-formed values `0..5` anyway, so the clamp
is pure defense-in-depth against a future caller or a programming
error, not a user-facing validation that needs to exist. A
raise would turn an easily-recoverable mistake into a hard crash for
no behavioral benefit in the one real call site that exists today.

### `set_entry_rating`'s no-op/dirty-save structure

Mirrors `set_entry_favorite` exactly: look up the entry via
`_require_entry`, clamp the incoming value, return early (no
`library.updated_at` bump, no `_save_catalog()` call) if the clamped
value equals the entry's current `rating`, otherwise mutate the entry,
bump `library.updated_at`, and save.

### `UserRole` offset: `UserRole + 3`

`FilmstripView` already uses `Qt.ItemDataRole.UserRole` (the path),
`UserRole + 1` (status), and `UserRole + 2` (favorite, a `bool`) on
each `QListWidgetItem` -- confirmed by grepping every `UserRole` use in
`filmstrip_view.py` before picking a value. Rating is stored at
**`UserRole + 3`** (an `int`, `0..5`), the next unused offset, set in
`_apply_entry_payload()` alongside the other three and read back in
`_show_context_menu()`The "Set Rating" submenu's six actions carry their
target rating value directly in a `dict[QAction, int]` built inline
while the submenu is constructed (mirroring how the Favorite action's
toggle target is computed from the item's stored `UserRole + 2` data),
so `UserRole + 3` is primarily consumed by tests and by any future
code that wants to read an item's current rating directly off the
widget without re-querying the controller.

### Tooltip-only rating display

In `_apply_entry_payload()`:

```python
favorite = bool(payload.get("favorite", False))
rating = _clamp_rating(payload.get("rating", 0))
item.setText("★" if favorite else "")
tooltip = str(payload.get("tooltip") or Path(str(payload["path"])).name)
prefix = ("Favorite\n" if favorite else "")
if rating > 0:
    prefix += f"Rating: {'★' * rating}{'☆' * (5 - rating)}\n"
item.setToolTip(prefix + tooltip)
```

`item.setText(...)` is unchanged -- it still only ever reflects
`favorite`. The rating-stars string is appended to the *tooltip*
prefix only, after the existing `"Favorite\n"` prefix (not instead of
it), so a favorited and rated image shows both lines
(`"Favorite\nRating: ★★★☆☆\n<name>"`); an unfavorited rated image
shows only the rating line; an unrated image (rating `== 0`) adds
nothing, exactly matching the un-favorited case's existing behavior of
adding nothing.

### "Set Rating" context-menu submenu

`_show_context_menu()` was extended in place (not duplicated) to add a
`QMenu("Set Rating")` submenu via `menu.addMenu(...)`, alongside the
existing Favorite toggle action, with six actions ("No Rating", "★
(1)" through "★★★★★ (5)"), each mapped to its integer value in a
local `dict[QAction, int]` built while the submenu is constructed.
After `menu.exec(...)` returns the selected action (or `None`), the
handler branches: the Favorite action still emits `favorite_toggled`
exactly as before; any of the six rating actions emits the new
`rating_changed = pyqtSignal(str, int)` signal with the item's path
and that action's mapped rating value.

### `LibraryController`/`MainWindow` wiring

`LibraryController.set_entry_rating(file_path, rating)` mirrors
`set_entry_favorite` exactly: guard on `_current_library_id`/
`file_path`, delegate to
`self._catalog_service.set_entry_rating(self._current_library_id, file_path, rating)`,
then `self._emit_libraries()` and
`self._rebuild_entries_for_current_library()` the same way. No
`"rating_count"` aggregate was added to `_emit_libraries()`'s
per-library payload -- Favorites has `"favorite_count"` only because
it feeds the Favorites filter row's count badge in `library_view.py`,
which Ratings is not getting in this slice (see Non-goals). `"rating"`
*was* added to both of `LibraryController`'s per-entry payload dict
literals (`_entry_payload()` and `_on_thumbnail_ready()`), alongside
their existing `"favorite": entry.favorite` line, so the filmstrip
actually receives each entry's rating value regardless of whether the
entry's thumbnail was already cached or is delivered asynchronously.

`MainWindow` adds one line, immediately below the existing favorite
wiring:

```python
self._filmstrip_view.rating_changed.connect(
    self._library_controller.set_entry_rating
)
```

## 4. Contracts

- `LibraryEntry.rating: int = 0` -- new dataclass field, threaded
  through `to_dict()`/`from_dict()`.
- `LibraryCatalogService.set_entry_rating(self, library_id: str, path: str, rating: int) -> LibraryEntry`
  -- new method; clamps `rating` to `0..5`; no-op (no save, no
  `updated_at` bump) if the clamped value is unchanged.
- `LibraryController.set_entry_rating(self, file_path: str, rating: int) -> None`
  -- new method; delegates to the catalog service against
  `self._current_library_id`, then refreshes views exactly like
  `set_entry_favorite`.
- `LibraryController._entry_payload()`/`_on_thumbnail_ready()` per-entry
  payload dicts both now include `"rating": entry.rating`.
- `FilmstripView.rating_changed = pyqtSignal(str, int)` -- new signal
  (path, new rating `0..5`), emitted by the context menu's "Set
  Rating" submenu actions.
- `FilmstripView` stores an item's rating at
  `Qt.ItemDataRole.UserRole + 3` (an `int`, `0..5`), alongside the
  existing `UserRole` (path), `UserRole + 1` (status), `UserRole + 2`
  (favorite).
- `MainWindow` connects `self._filmstrip_view.rating_changed` to
  `self._library_controller.set_entry_rating`.
- No existing method's signature or behavior changed. `favorite`'s
  item text, tooltip prefix, `UserRole + 2` data, context-menu action,
  and `favorite_toggled` signal are all unmodified.

## 5. Nuances and failure modes

**Old catalog files predating this slice.** A catalog JSON file
written before this slice has no `"rating"` key on any entry at all.
`LibraryEntry.from_dict()`'s `payload.get("rating", 0)` already
defaults cleanly to `0` before `_clamp_rating` even runs, so loading
an old catalog produces entries with `rating == 0` for every image,
with no migration step and no error. This is pinned directly by a
test that builds a `LibraryEntry.from_dict()` payload with no
`"rating"` key (and, separately, no `"favorite"` key) and asserts both
default to their falsy/zero values.

**Corrupt or out-of-range persisted values.** A hand-edited or
corrupted catalog file could contain `"rating": "oops"` or
`"rating": 99` or `"rating": -4`. `_clamp_rating()` coerces all three
to a safe in-range `int` (`0`, `5`, `0` respectively) rather than
raising or propagating an invalid value into the UI -- pinned by
dedicated tests for both a non-numeric value and both out-of-range
directions.

**`set_entry_rating` on an out-of-range input.** Clamps rather than
raises (see Design's "Clamp vs. raise" above) -- a call with
`rating=-3` or `rating=99` succeeds and stores `0`/`5` respectively,
never raising `ValueError`.

**Favorite and rating coexisting in one tooltip.** Explicitly tested:
a favorited, rated entry's tooltip is
`"Favorite\nRating: ★★★★★\n<name>"` -- both lines present, neither
overwriting the other, in favorite-then-rating order (matching the
order the prefix is built in code).

**Favorite-only regression.** The pre-existing favorite-only item
text/tooltip test (`test_filmstrip_filters_favorites_and_sorts_by_name`)
was left completely unmodified and still passes; a new, explicit
regression test
(`test_filmstrip_favorite_only_tooltip_and_text_are_unchanged`) pins
the exact favorite-only text/tooltip/`UserRole + 2` values once more,
confirming this slice's addition did not silently alter them.

## 7. Rollout

Purely additive: one new dataclass field (`LibraryEntry.rating`,
default `0`, so every existing in-memory/freshly-loaded entry is
unaffected), one new catalog-service method, one new controller
method, two new dict keys added to existing payload literals, one new
`FilmstripView` signal plus an extended (not replaced) context menu,
and one new `MainWindow` connect call. No existing method's signature
changed. A plain revert removes the feature entirely; any `"rating"`
keys already written to a catalog file by this feature become inert,
unread leftover JSON if the feature is removed later (the same
revert-safety story "Import presets" documented for its own leftover
settings key).
