# Vignette adjustment

Related roadmap: Phase G / PDF section 16. Related workflow: `INCREMENTAL_WORKFLOW.md` sections 4 and 5.1.
Related prior slices: docs/planning/implementation-notes/2026-09-30-texture.md,
docs/planning/implementation-notes/2026-10-12-clarity.md,
docs/planning/implementation-notes/2026-10-12-dehaze.md.

## 1. Problem, goal, and non-goals

Texture, Clarity, and Dehaze are implemented, but PhotoEdit still has no
periphery-darkening (or lightening) control. This slice adds one
neutral-by-default Vignette control. Unlike Texture, Clarity, and Dehaze --
all blur-based operations (two signed-residual local-contrast tricks plus a
veil-estimate-and-blur haze model) -- Vignette is a genuinely different
operation again: a purely spatial radial mask built from each pixel's
normalized distance from the image center, with no blurring involved at
all. It does not add Grain, sharpening, or noise reduction. It does not add
Lightroom's full vignette sub-panel (Midpoint, Roundness, Feather,
Highlights) -- only the single "Amount" strength slider, matching how
Texture/Clarity/Dehaze each shipped as a single slider; the sub-controls are
deferred to a future slice if ever requested.

## 2. Current behavior

`ToolsPanel` emits flat basic adjustments; `ImageController` owns normalized
state and coordinates preview/final rendering; `ProcessingRequest` and
`ProcessingWorker` carry category dictionaries; `CombinedAdjustmentCommand`
provides the synchronous undo fallback. Dehaze is currently the final
pipeline stage, applied right after Clarity (which runs right after
Texture, which runs right after Color Grading).

## 3. Design and flow

Add a fourth -100..100 Vignette slider to the existing Effects section,
directly below Dehaze. Vignette remains a top-level persisted float for
consistency with other single-slider controls, while processing APIs carry
`{"vignette": value}` as a separate category, following
Texture/Clarity/Dehaze's wiring pattern exactly. The controller sends it
through preview, final, synchronous, restore, export, reset, and history
paths. The worker applies it after Dehaze and includes it in preview cache
signatures. Pipeline order is now
... Color Grading -> Texture -> Clarity -> Dehaze -> Vignette -> ... .

`VignetteProcessor` builds a normalized radial distance field from the
image center: for an `(H, W, C)` image it computes pixel-center-relative
`dy`/`dx` normalized by half-height/half-width respectively (so the field
is aspect-ratio-correct rather than assuming a square image), then
`radius = sqrt(dx**2 + dy**2) / sqrt(2)`, clipped to `[0, 1]` (`0` at the
exact center, `1` at the farthest corner). A cubic smoothstep
(`t*t*(3-2*t)`) ramps from a fixed midpoint (`0.6`) out to `1.0`, so the
mask is exactly `0` inside the midpoint radius (center stays untouched) and
rises smoothly to `1` at the far corners -- no `cv2.GaussianBlur` or other
blur-based smoothing is used anywhere in this processor, which is the
central way it differs from Texture/Clarity/Dehaze. Positive values
(0..100, darken) multiply the source by `1 - edge_t * strength`. Negative
values (-100..0, lighten) push peripheral pixels toward white
(`source + (1.0 - source) * edge_t * strength_magnitude`), deliberately
left unclipped so a pixel already above 1.0 keeps its headroom. It operates
per channel on float32 linear-light data and does not clip intermediate
values. Zero returns immediately.

The scale and operation are both deliberately distinct from Texture
(`sigma=2`, signed residual), Clarity (`sigma=20`, signed residual), and
Dehaze (`sigma=15`, veil-estimate-and-rescale) -- the same "distinct
scales/semantics" requirement flagged when Clarity and Dehaze were added
(clarity note section 5, dehaze note section 3) applies here too, and
Vignette goes further still: it has no blur sigma attribute at all, since
no blurring occurs anywhere in the formula.

## 4. Contracts and compatibility

- State key: `vignette`, finite numeric float, default `0.0`.
- UI and processor range: `-100..100`; processor clamps out-of-range callers.
- Older payloads that omit the key restore as zero.
- No schema-version bump is needed because this is an additive defaulted key.
- No dependency is added; NumPy alone is sufficient (no OpenCV call at all,
  unlike Texture/Clarity/Dehaze).

## 5. Nuances and failure modes

Constant/neutral images must not develop a color cast: because the radial
mask is the same 2-D field broadcast identically across all three channels,
a constant input stays channel-equal after processing (its overall level
may shift radially, which is the intended vignette effect). 1x1 images must
not divide by zero: `half_h`/`half_w` are each floored at `1e-6` before
being used as divisors, and for a genuinely 1x1 image the single pixel sits
exactly at the computed center (`radius == 0`), so the mask is a no-op
there regardless. Non-square images are handled by normalizing `dy` and
`dx` independently by half-height and half-width before combining them,
rather than assuming a square aspect ratio -- a wide image's vignette
reaches full strength at the left/right edges' corners, not partway along
the long edges, matching Lightroom's elliptical-on-non-square behavior at
the simplest "Amount"-only level. Output shape/dtype are retained. The
effect is intentionally an approximation of Lightroom's simplest vignette
control, not a claim of matching its full Midpoint/Roundness/Feature math.

## 6. UI/reskin, dependencies, and performance

The view contains only the slider and emits plain data; all math stays in
the processor. Existing throttling, cancellation, interactive proxies,
quality preview, and delayed full-resolution rendering remain unchanged.
The radial field is built once per call from 1-D row/column vectors
broadcast together (no per-pixel Python loop, no blur pass), so it is
cheaper than Texture/Clarity/Dehaze's Gaussian blurs and was not observed
to be a bottleneck in the automated suite. Any later Phase G slices (Grain,
sharpening, noise reduction) must continue to use distinct scales/semantics
from Texture, Clarity, Dehaze, and Vignette. Lightroom's fuller vignette
sub-controls (Midpoint, Roundness, Feather, Highlights) remain deferred
non-goals per section 1; if ever requested, they would extend this single
`vignette` float into a small nested params dict (following the
HSL/Color-Grading nested-dict precedent) rather than changing this slice's
contract.

## 7. Test plan and manual smoke

Automated coverage pins identity/copy behavior at zero, positive vignette
darkening corners more than the center on a constant bright image,
negative vignette lightening corners more than the center, a 1x1 image not
dividing by zero, a non-square image still darkening corners more than
center, constants/neutrals staying channel-equal in both directions,
dtype/shape/headroom, parameter clamping in both directions, a
no-blur-sigma distinctness check against Texture/Clarity/Dehaze, UI
range/emission/restore, queue and worker propagation/skip behavior,
controller persistence/export/undo, and command undo -- mirroring
Texture/Clarity/Dehaze's test structure file-for-file. Run the complete
suite.

Manual: open an image; move Vignette positive and negative; verify a
responsive preview, final render on release, undo/redo, reset, image-switch
restore, and export, with Texture, Clarity, Dehaze, and Vignette active
together.

## 8. Rollout, rollback, and acceptance

The feature is additive and identity-defaulted. A plain revert removes it;
older builds ignore the extra persisted key. Acceptance requires the full
vertical path, no UI-thread image math, backward-compatible restore, passing
targeted/full tests, clean diff checks, and honest manual-test reporting.

Plan approved -- implementation allowed: mirrors the approved Texture/
Clarity/Dehaze slices' scope and wiring pattern (2026-10-12).

## 9. Implementation summary

Implemented `VignetteProcessor` (aspect-ratio-correct radial distance
field, cubic-smoothstep falloff from a midpoint of `0.6`, no blur -- a
distinct formula shape from Texture/Clarity's signed-residual approach and
from Dehaze's veil-estimate-and-rescale approach) and wired it through
every integration point Dehaze touches: `ImageController` (defaults,
processor/params state, preview/final/sync rendering, export,
restore/export state, reset, `apply_adjustments`, the four `on_*_changed`
debounced paths, slider-release, `_has_pending_adjustment_changes`, delayed
final render, and `commit_adjustments`), `ProcessingRequest`/
`ProcessingQueue`, `ProcessingWorker` (processor, submit/apply/cache-key/
signature, perf logging), `CombinedAdjustmentCommand`'s synchronous
fallback, and a fourth "Vignette" slider in `ToolsPanel`'s Effects section
below Dehaze. Vignette is applied immediately after Dehaze everywhere in
the pipeline. No unrelated code was touched; the roadmap coverage table and
git history are left for the calling session.

Two existing exact-dict contract tests in `test_image_controller.py`
(`test_get_adjustment_state_returns_normalized_defaults` and
`test_restore_adjustment_state_applies_saved_values`) asserted the complete
`get_adjustment_state()` payload key-for-key and needed a `"vignette": 0.0`
entry added alongside the other now-13 top-level float keys, the same kind
of necessary update each of Texture/Clarity/Dehaze's own additions would
have required of this pair of tests.

Verification: targeted new/changed tests (processor + controller + command
+ queue + worker + tools-panel Vignette tests, run alongside the full
Dehaze/Clarity/Texture suites they extend) **195 passed**; complete suite
**675 passed, 1 deselected in 105.69s** (the pre-existing
`test_geometry_is_restored_on_next_launch` offscreen flake noted in the
Texture/Clarity/Dehaze notes persists and was deselected, not fixed, per
the task instructions). A live GUI smoke test was not performed in this
non-interactive environment.
