# Defringe (Optics) adjustment

Related roadmap: Phase H / PDF section 18. Related workflow:
`INCREMENTAL_WORKFLOW.md` sections 4 and 5.1.
Related prior slice: docs/planning/implementation-notes/2026-10-12-remove-chromatic-aberration.md
(this slice's direct predecessor and wiring template).

## 1. Problem, goal, and non-goals

Phase H ("Optics", PDF section 18) started with Remove CA (a profile-free
geometric approximation of lateral chromatic aberration correction).
That note's own non-goals section explicitly named "Defringe" as the
*next* slice -- this slice. Defringe adds a second, final "Optics"
control: a single `0..100` "Defringe" slider, placed directly after
Remove CA in the existing "Optics" `ToolsPanel` section (no new
section is created). It targets a genuinely different artifact with a
genuinely different mechanism from Remove CA:

- Remove CA corrects a **spatial misregistration** between channels (a
  geometric remap).
- Defringe desaturates a **residual color artifact** -- purple/magenta
  or green fringing that tends to survive at high-contrast edges even
  after (or without) geometric CA correction -- via **hue-and-edge-gated
  local desaturation**, a color-domain operation, not a geometric one.

**Non-goals, and why they are real gaps, not just "later":**

- **Separate purple/green hue-RANGE sliders, or per-color "Amount"
  sliders.** Lightroom's full Defringe panel exposes independent
  Purple Amount/Hue-range and Green Amount/Hue-range controls (4
  sub-sliders plus 2 range pickers). This slice implements a single
  `0..100` "Defringe" amount that applies **both** hue bands at once
  with **fixed** band centers/widths (see section 3). This is a
  deliberate scope reduction to "one slider, like every other
  Optics/Detail control in this codebase" rather than introducing a
  new multi-control sub-panel pattern for a single feature.
- **"Enable Lens Corrections" (profile-based distortion/vignetting/CA
  correction).** Unchanged from the Remove CA note -- still a durable,
  structural gap (no lens profile database, no profile file format, no
  camera/lens metadata extraction pipeline, no profile-selection UI).
  See the Remove CA note section 1 for the full explanation; it applies
  unchanged here.
- **Phase H is now complete** for this codebase's two feasible
  algorithmic Optics controls (Remove CA, Defringe). The profile-based
  gap above is the one remaining, permanent item in this PDF section,
  not a "next slice."

## 2. Current behavior

`ToolsPanel`'s "Optics" section (added by the Remove CA slice, placed
after "Detail") currently holds one slider, "Remove CA", with its own
"Reset Optics" header button. `ImageController` threads `remove_ca`
through defaults, processor/params state, preview/final/sync
rendering, export, restore/export state, reset, `apply_adjustments`,
the four `on_*_changed` debounced paths, slider-release,
`_has_pending_adjustment_changes`, delayed final render, and
`commit_adjustments`. `ProcessingRequest`/`ProcessingQueue` and
`ProcessingWorker` thread `remove_ca_params` as a request field, apply
it in the worker, and include it in the preview-cache
signature/cache-key. `CombinedAdjustmentCommand` applies it in its
synchronous undo-fallback path. Remove CA runs last in the pipeline
(after Color NR), everywhere.

## 3. Design and flow

Add a second slider, "Defringe" (`0..100`, default `0.0`), to the
*existing* "Optics" section, immediately after "Remove CA", and include
it in the same "Reset Optics" button's slider list (so resetting Optics
now clears both sliders together). No new section, icon, or header
widget is added. `DefringeProcessor`
(`src/processors/defringe_processor.py`) threads through every
integration point Remove CA threads through, by direct analogy
(`defringe_processor`/`_defringe_params`/`defringe_params`, mirroring
`remove_ca_processor`/`_remove_ca_params`/`remove_ca_params`). Defringe
is applied immediately **after** Remove CA everywhere in the pipeline,
making the full, final Phase G+H pipeline order: ... Luminance NR ->
Color NR -> Remove CA -> Defringe. This is a natural fit conceptually
(Defringe cleans up a residual of the kind of artifact Remove CA
targets) as well as mechanically (it is simply the next append in the
same fixed five-call-site append chain Remove CA's own note documents
at length in its section 5 -- that rationale is not repeated here since
nothing about it changes for this slice).

`DefringeProcessor` does **not** reuse Remove CA's geometric-remap
math, or any other prior processor's math wholesale -- it is a
**hue-and-edge-gated local desaturation**, the first processor in this
codebase to gate an intensity operation on *both* a spatial edge
condition *and* a hue-band condition simultaneously:

```
Y = 0.2126*R + 0.7152*G + 0.0722*B                  # Rec.709 luminance

gx = cv2.Sobel(Y, cv2.CV_32F, 1, 0, ksize=3) / 8.0
gy = cv2.Sobel(Y, cv2.CV_32F, 0, 1, ksize=3) / 8.0
grad_mag = sqrt(gx**2 + gy**2)
edge_mask = grad_mag / (grad_mag + 0.1)             # soft 0..1 ratio

c = clip(source, 0, 1)                              # hue/chroma only;
r, g, b = c[...,0], c[...,1], c[...,2]               # output pixels are
maxc, minc = max(r,g,b), min(r,g,b)                  # never clipped
delta = maxc - minc
safe_delta = where(delta < 1e-6, 1.0, delta)
hue_r = 60 * (((g - b) / safe_delta) % 6)
hue_g = 60 * (((b - r) / safe_delta) + 2)
hue_b = 60 * (((r - g) / safe_delta) + 4)
hue = where(maxc == r, hue_r, where(maxc == g, hue_g, hue_b))
chroma_weight = clip(delta / 0.05, 0, 1)

purple_membership = exp(-0.5 * (circular_hue_distance(hue, 290) / 25)^2)
green_membership  = exp(-0.5 * (circular_hue_distance(hue, 110) / 25)^2)
hue_mask = clip(purple_membership + green_membership, 0, 1) * chroma_weight

strength = (defringe / 100.0) * edge_mask * hue_mask
neutral = stack([Y, Y, Y])
result = source + strength * (neutral - source)
```

The edge mask reuses the exact soft-ratio pattern Sharpening's own
edge-aware mask already established in this codebase
(`mask = x / (x + epsilon)`, see `src/processors/sharpening_processor.py`):
a cheap, smooth 0..1 ramp from "no local contrast" to "strong local
contrast," with no hard threshold. Defringe's own epsilon (`0.1`) is
tuned for Sobel's larger raw gradient-magnitude scale (Sharpening's
`detail = source - blurred` residual lives in a much smaller numeric
range than a `/8`-normalized Sobel gradient), not copied verbatim from
Sharpening's `0.02`.

Hue and chroma are computed from a **clipped-to-[0,1] copy** of the
source (`c = clip(source, 0, 1)`), but that clipping is used **only**
for the hue/chroma computation -- `strength` is then applied to the
*original, unclipped* `source` in the final blend. This means an
HDR pixel above `1.0` still gets a sensible hue classification (based
on its in-range-clamped color ratios) without the processor's actual
*output* ever being clipped, preserving headroom exactly like every
other Effects/Detail/Optics processor in this codebase.

## 4. Contracts and compatibility

- State key: `defringe`, finite numeric float, default `0.0`.
- UI and processor range: `0..100` (one-directional -- there is no
  "add fringing" creative use case, matching Remove CA/Grain/
  Sharpening/Luminance NR/Color NR precedent); the processor clamps
  out-of-range callers (including negative values, which clamp to `0`,
  i.e. identity).
- Older payloads that omit the key restore as zero.
- No schema-version bump is needed because this is an additive
  defaulted key.
- `cv2` (already a dependency) is reused for `cv2.Sobel`; this is a
  new *function* from that same dependency (Remove CA already uses
  `cv2.remap`; Sharpening/Texture/etc. already use `cv2.GaussianBlur`),
  not a new package.
- The roadmap coverage table's PDF-18 row was updated to read "Remove
  CA and Defringe implemented; no lens-profile-based corrections (no
  profile database exists -- durable gap)," replacing the previous
  wording that listed Defringe as remaining.

## 5. Nuances and failure modes

**Why 25 degrees for the hue-band half-width, and how it was checked.**
The Gaussian membership function
`exp(-0.5 * (circular_hue_distance(hue, center) / width)^2)` is a soft
bump, not a hard range: at `width = 25`, membership is `1.0` exactly at
the center hue, `~0.61` at `±25` degrees out (one "sigma"), and
`~0.14` at `±50` degrees out, decaying smoothly rather than cutting off.
This value was chosen as a middle ground and then checked empirically
against the synthetic test fixtures built for this slice (see section
7): at `width = 25`, a strongly saturated purple fringe strip
(`hue ~= 294`, 4 degrees from the 290-degree center) sitting at a
high-contrast edge loses roughly a quarter of its chroma at full
strength, while the identical purple hue in a completely flat
(gradient-free) region loses effectively none (`<1e-4` relative, i.e.
numerically exact -- the edge mask is exactly zero on a perfectly
uniform image under Sobel, see below) -- a clear, well-separated
discrimination between "fringe" and "ordinary saturated color," which
is the property this processor exists to have. A still-saturated but
clearly *off-band* hue (orange, `hue ~= 20`, which is `90` degrees from
both the `290` purple and `110` green centers) loses under `2%` of its
chroma even sitting at the exact same kind of high-contrast edge --
confirming the hue gating, not just the edge gating, is doing real
discriminating work. Narrower widths were considered but not used:
Lightroom's own fringe hues vary by lens/aperture/defocus amount more
than a very narrow band (e.g. `10` degrees) would tolerate, and `25`
degrees was wide enough to catch that variation in informal testing
while still leaving `90`-degree-distant hues like orange/red/yellow and
cyan/blue subject matter almost untouched.

**Why edge-gating (not just hue-gating) is the essential property, and
how the test actually distinguishes the two.** A processor that simply
desaturated every purple/green pixel regardless of position would also
"fix" fringing, but would be a strictly worse user control -- it would
visibly wash out purple flowers, green foliage, amethyst, etc. anywhere
in the frame, not just at lens-fringe edges. The dedicated test
(`test_edge_purple_fringe_is_desaturated_but_flat_purple_is_not`) proves
the processor is *not* that simpler, worse thing: it builds one image
with a purple fringe strip at a genuine high-contrast luminance edge,
and a **second, entirely separate, perfectly flat** image filled with
the exact same purple color and no luminance variation anywhere. Both
get processed at `defringe=100` (maximum strength). The edge case loses
over `10%` of its chroma (comfortably exceeding the test's `0.1`
threshold); the flat case's chroma is unchanged to within `1e-5`
(effectively exact, since `cv2.Sobel` on a perfectly uniform array
returns an exact-zero gradient everywhere, so `edge_mask` is exactly
`0` and `strength` is exactly `0` at every pixel). The test asserts
both halves explicitly (`edge_loss > 0.1` and `flat_loss < 1e-4`) and
their relative comparison (`edge_loss > flat_loss + 0.1`), so a future
regression that accidentally drops the edge-gating term (making
Defringe hue-gated only) would fail the flat-image assertion directly,
not just produce a slightly-different-looking passing test.

**Tiny/degenerate images.** `cv2.Sobel` was verified directly (not
assumed) against `1x1`, `2x2`, and `3x3` float32 inputs before writing
this processor:

```
(1, 1): gx = [[0.]], gy = [[0.]]            -- no crash, zero gradient
(2, 2): gx = [[0. 0.] [0. 0.]], gy likewise -- no crash, zero gradient
(3, 3): gx/gy nonzero in the interior, finite throughout -- no crash
```

No crash or non-finite output occurred for any size. Since the
gradient comes back as all-zero for `1x1`/`2x2` inputs, `edge_mask` is
`0` everywhere for those sizes regardless of `defringe`, so the
processor is a safe (if trivial) no-op-equivalent identity-like pass
for genuinely degenerate images -- matching Remove CA's and Color NR's
"verify first, add no unneeded insurance" precedent (as opposed to
Luminance NR's precedent of adding a defensive bypass anyway) rather
than assuming `cv2.Sobel`'s border behavior from documentation alone.
`test_tiny_1x1_image_does_not_crash` and
`test_tiny_2x2_image_does_not_crash` pin this directly.

**No clipping for output, dtype/shape preserved.** Like every prior
Effects/Detail/Optics processor, Defringe does not clip its actual
output, preserving HDR headroom -- only the *internal* hue/chroma
computation clips a local copy, never the pixels that get returned
(see section 3). `test_preserves_dtype_shape_and_headroom_without_clipping`
pins this with a source pixel above `1.0`.

**Determinism.** `process()` is a pure, deterministic function of
`(image, defringe)` -- no RNG anywhere in Sobel, hue math, or the
blend. `test_is_deterministic_pure_function` pins two calls with the
same inputs as byte-identical.

**Near-neutral/gray pixels and `chroma_weight`.** When `delta` (max -
min across R/G/B) is very small, the hue formula's division becomes
numerically noisy (a near-gray pixel's "hue" can swing wildly for a
tiny color perturbation, since hue is undefined in the true-gray
limit). `chroma_weight = clip(delta / 0.05, 0, 1)` multiplies into
`hue_mask` specifically to suppress hue-band membership for such
pixels regardless of what (numerically unstable) hue value they
happen to compute to -- a near-gray pixel at a strong edge (e.g. the
flat gray blocks flanking a fringe strip in the test fixtures) is not
desaturated just because its noisy hue momentarily lands near 290 or
110 degrees.

## 6. UI/reskin, dependencies, and performance

The view adds only a second `AdjustmentSlider` ("Defringe",
`min_value=0.0, max_value=100.0`) to the existing "Optics"
`CollapsibleSection`, right after "Remove CA," and extends the
section's existing "Reset Optics" button's `_reset_sliders(...)` call
to reset both sliders. No new section, icon, or `CollapsibleSection`
construction is added -- this slice is Color NR's "extend an existing
section" precedent, not Sharpening's/Remove CA's "create a new
section" precedent, since Optics already exists from the Remove CA
slice. All math stays in the processor; existing throttling,
cancellation, interactive proxies, quality preview, and delayed
full-resolution rendering are unchanged. No new dependency is added
(`cv2.Sobel` is a new function from the existing `cv2` dependency).
Two Sobel convolutions plus a handful of elementwise array ops at full
resolution are comparable in cost to Sharpening's single Gaussian
blur call and were not observed to be a bottleneck against this
codebase's (small) synthetic test images; the `defringe == 0.0` early
return (skipping Sobel and all hue/chroma math entirely) is kept as
the no-op fast path, matching every other processor's convention.

**This completes Phase H's two feasible algorithmic Optics controls.**
After this slice, Remove CA and Defringe are both implemented;
profile-based "Enable Lens Corrections" remains the one documented,
durable, out-of-scope gap in Phase H, pending lens-profile
infrastructure that does not exist in this codebase today (section 1).

`np.array_equal`); the key edge-vs-flat discrimination behavior
described in section 5 (a purple fringe strip at a genuine edge loses

## 8. Rollout, rollback, and acceptance

The feature is additive and identity-defaulted. A plain revert removes
it; older builds ignore the extra persisted key. Acceptance requires
the full vertical path, no UI-thread image math, backward-compatible
restore, passing targeted/full tests, clean diff checks, and honest
manual-test reporting.

## 9. Implementation summary

Implemented `DefringeProcessor` (`src/processors/defringe_processor.py`):
a deterministic hue-and-edge-gated local desaturation, the first
processor in this codebase to combine a Sobel-gradient edge mask with a
circular-Gaussian hue-band membership mask. It computes Rec.709
luminance, a soft Sobel-based edge-strength mask (reusing Sharpening's
established `x / (x + epsilon)` soft-ratio pattern), and a purple
(`290`-degree center) / green (`110`-degree center) hue-band membership
mask (each a `25`-degree-half-width circular Gaussian bump, weighted
down for near-neutral pixels via a chroma gate), then desaturates each
pixel toward its own luminance by `strength = (defringe/100) *
edge_mask * hue_mask`. Hue/chroma are computed from a clipped-to-[0,1]
copy of the source so HDR values still classify sensibly, but the
actual output is never clipped. One-directional `0..100` range; zero
returns an identity copy without computing Sobel gradients or hue/
chroma at all.

Wired it through every integration point Remove CA touches:
`ImageController` (defaults, processor/params state, preview/final/sync
rendering, export, restore/export state, reset, `apply_adjustments`,
the four `on_*_changed` debounced paths, slider-release,
`_has_pending_adjustment_changes`, delayed final render, and
`commit_adjustments`), `ProcessingRequest`/`ProcessingQueue`,
`ProcessingWorker` (processor, submit/apply/cache-key/signature, perf
logging), `CombinedAdjustmentCommand`'s synchronous fallback, and a
second "Defringe" slider (`min_value=0.0, max_value=100.0`) added to
the *existing* "Optics" `CollapsibleSection` right after "Remove CA,"
included in that section's existing "Reset Optics" button's slider
list. Defringe is applied immediately after Remove CA at the very end
of the pipeline, after Color NR -- the natural next append in the same
fixed five-call-site append chain Remove CA's own note already
documents the rationale for. No unrelated code was touched; no new
section, icon, or `CollapsibleSection` was created.

**Hue-band width.** `25` degrees (half-width of the Gaussian bump
around each of the `290`-degree purple and `110`-degree green hue
centers) was chosen as a middle ground and then checked directly
against the synthetic test fixtures built for this slice: it gives a
clear, well-separated discrimination between a purple/green fringe
strip at a genuine high-contrast edge (over 10% chroma loss at full
strength) and the same purple hue in a perfectly flat, gradient-free
image (under `1e-4` relative chroma loss, i.e. numerically exact), while
an equally-saturated but off-band hue (orange, `90` degrees from both
centers) at the same kind of edge loses under `2%` -- confirming the
hue gating discriminates by color, not just by edge strength. See
section 5 for the full reasoning.

**Edge-gating verification.** The dedicated test
`test_edge_purple_fringe_is_desaturated_but_flat_purple_is_not` was
built specifically to rule out the simpler, strictly worse alternative
design (global purple/green desaturation with no edge gating at all):
it processes two separate images -- one with a purple fringe strip at
a real luminance edge, one perfectly flat and uniformly purple -- at
identical maximum strength, and asserts the edge case loses
substantially more relative chroma than the flat case (which loses
effectively none, confirmed via `cv2.Sobel`'s exact-zero gradient on a
uniform array). This both demonstrates and pins the specific claim this
slice's design depends on.

**Tiny images.** `cv2.Sobel` was verified directly against `1x1`,
`2x2`, and `3x3` float32 inputs before writing the processor and did
not crash or misbehave on any of them (both `1x1` and `2x2` return an
exact-zero gradient under Sobel's border handling, meaning Defringe is
effectively a no-op on genuinely degenerate images regardless of
`defringe`), so no defensive bypass was added -- matching Remove CA's
and Color NR's "verify first, add no unneeded insurance" precedent.

As with the Remove CA slice, the two existing exact-dict contract tests
in `test_image_controller.py`
(`test_get_adjustment_state_returns_normalized_defaults` and
`test_restore_adjustment_state_applies_saved_values`) needed a
`"defringe": 0.0` entry added alongside the other now-19 top-level
float keys. Unlike the Remove CA slice, no `ToolsPanel` reset-button
index needed renumbering, since Defringe extends the existing Optics
section/button rather than inserting a new section after it.

**Deviation note.** None of substance: the task's design spec was
followed as given for the processor math, hue-band centers, edge-mask
pattern reuse, and state-key/range contract. The one judgment call
documented explicitly (per the task's own instruction to "document
whatever you land on and why" for the hue-band width) was keeping the
suggested `25`-degree half-width rather than tuning it further, since
the empirical check against this slice's own synthetic test fixtures
already showed a clear, comfortably-separated discrimination between
edge-fringe and flat-saturated-color at that value.
