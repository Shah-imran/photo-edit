# Keywords (free-text per-entry tags, JSON via LibraryCatalogService)

Related roadmap: Phase A, "Library DAM and workspace chrome" (PDF
sections 8-9, 24) in `docs/planning/PRODUCT_ROADMAP.md` -- the bullet
"**Ratings** and **pick/reject** (or flags); **keywords** on disk or
sidecar (design choice: XMP vs JSON)." The prior two slices
(`docs/planning/implementation-notes/2026-10-13-ratings.md` and
`docs/planning/implementation-notes/2026-10-13-pick-reject-flags.md`)
built Ratings and pick/reject flags, each explicitly deferring
keywords as "a separate, still-undone gap." This note is that slice,
and it closes the last remaining gap in this roadmap bullet.

This is library-metadata plumbing mirroring the same per-image
metadata features already complete in this codebase -- **Favorite**
(`bool`), **Rating** (`int` 0-5), and **Flag** (tri-state `str`) --
with one structural difference: a keyword list is a *non-scalar*
JSON-safe value (`list[str]`), so its closest precedent is actually
`LibraryEntry.adjustment_state: Optional[dict]`, which already
round-trips a non-scalar JSON-safe value through
`to_dict()`/`from_dict()` via the existing `_optional_dict()` helper.

## 1. Problem, goal, and non-goals

**Problem.** There was no way to attach free-text tags ("sunset",
"family", "client-x") to a library image, independent of rating,
favorite, or pick/reject state. Lightroom calls this Keywording; the
roadmap bullet calls it out explicitly, including as an open design
question ("XMP vs JSON").

**Design choice: JSON, via the existing `LibraryCatalogService` --
not an XMP sidecar.** This codebase already persists all other
per-entry metadata (`favorite`, `rating`, `flag`, `adjustment_state`)
as plain JSON fields inside the single catalog file written by
`LibraryCatalogService`, not as XMP sidecar files written next to each
source image. Keywords, like those four fields, are app-internal
per-entry metadata in this slice -- there is no requirement here that
another tool (Lightroom, Bridge, etc.) be able to read or write the
same keyword data from a `.xmp` file sitting beside the source image.
Building XMP sidecar support would mean an entirely different
persistence mechanism: writing and reading a real `.xmp` file per
image, handling XMP packets that may already exist (written by other
tools, possibly with their own non-keyword fields that must be
preserved on write), and the general cross-tool-interop surface that
comes with that -- a real, standalone feature, not a one-line
difference in how this slice stores a list of strings. That is out of
scope here and, if cross-tool interop with other DAM/editing tools
ever becomes a real requirement, is a separate, larger future slice.
For this slice, keywords are simply one more field on `LibraryEntry`,
following the exact same JSON-via-catalog-service convention as
`favorite`/`rating`/`flag`/`adjustment_state`.

**Goal.** Add a `keywords: list[str]` field to `LibraryEntry`
(via `dataclasses.field(default_factory=list)` -- see Design below for
why this matters), a `LibraryCatalogService.set_entry_keywords()`
setter, a `LibraryController.set_entry_keywords()` delegate, a
`FilmstripView` context-menu item ("Edit Keywords...") backed by a
`QInputDialog.getText()` comma-separated editor emitting
`keywords_changed`, and the one-line `MainWindow` wiring connecting
the two -- the same five layers Favorite/Rating/Flag already use,
mirrored field-for-field and method-for-method, adapted where the
list-vs-scalar difference requires it.

**Non-goals (explicit scope boundary for this slice):**

- **No bulk/multi-select keyword editing across several images at
  once.** Checked directly before writing this note: neither
  `FilmstripView`'s `QListWidget` (`src/views/widgets/filmstrip_view.py`)
  nor the library grid/panel sets any `QAbstractItemView.SelectionMode`
  other than the Qt default (`SingleSelection`) anywhere in `src/` --
  confirmed by grepping every `SelectionMode`/`ExtendedSelection`/
  `MultiSelection` reference in `src/`, which returns no results at
  all. This codebase has no multi-select UI in the filmstrip or
  library grid to batch-apply keywords (or any other per-entry
  metadata) to in the first place, so "no multi-select keyword
  editing" isn't a feature being deliberately deferred so much as a
  feature with no selection mechanism to build on yet; a future slice
  that adds multi-select would need to add batch-apply for Favorite/
  Rating/Flag too, not just keywords.
- **No keyword-based search/filter integration with the filmstrip
  search box** added in the immediately prior slice
  (`docs/planning/implementation-notes/2026-10-13-filmstrip-search.md`).
  `FilmstripView._render_entries()`'s search predicate still matches
  only `filename`/`path`; extending it to also match keyword text is a
  reasonable, natural follow-up, but is explicitly deferred, not built
  here.
- **No autocomplete or suggested-keywords UI.** The editor is a plain
  `QInputDialog.getText()` comma-separated text field, pre-filled with
  the item's current keywords -- no keyword-history dropdown, no
  cross-entry keyword suggestion list, no keyword hierarchy/synonyms
  (all Lightroom Keywording-panel features). Nothing that broad was
  needed to close this roadmap gap.
- **No dedicated "Keywords" filter/collection entry in the library
  sidebar**, matching Ratings' and Flags' own non-goal: no new sidebar
  row, no new `_filter_mode` value for keywords. Keywords are surfaced
  via the filmstrip item's **tooltip only** (see Design below), the
  same way Rating and Flag are.
- **No keyword-based sorting.** `FilmstripView`'s existing sort
  control (`"added"`/`"name"`) is untouched.
- **No change to the existing favorite "★" item-text display.** The
  item's `text()` is still reserved for the favorite marker only;
  keywords (like rating and flag) are tooltip-only.

This completes the full roadmap bullet: Ratings, pick/reject flags,
and keywords are now all **Done**. The bullet itself, and the
"Coverage vs current PhotoEdit" table's PDF row 4, are updated below
to reflect that.

## 2. Current behavior (before this slice)

`LibraryEntry` had `favorite: bool`, `rating: int`, and `flag: str`
but no notion of keywords at all. `FilmstripView`'s
`_apply_entry_payload()` read `payload.get("favorite", False)`,
`payload.get("rating", 0)`, and `payload.get("flag", "none")` to build
the item's text/tooltip/stored `UserRole` data; its
`_show_context_menu()` had a Favorite toggle, a "Set Rating" submenu,
and three flat Pick/Reject/Remove-Flag actions, but nothing for
keywords. `LibraryController._entry_payload()`/`_on_thumbnail_ready()`
already included `"favorite"`, `"rating"`, and `"flag"` in both
per-entry payload dicts; neither included `"keywords"`, because there
was nothing to include.

## 3. Design

### Representation: `list[str]`, via `field(default_factory=list)`

Keywords are a plain `list[str]` field
(`keywords: list[str] = field(default_factory=list)`), following the
`adjustment_state: Optional[dict] = None` precedent for a non-scalar
JSON-safe field rather than `favorite`/`rating`/`flag`'s scalar
precedent. **Crucially, the default is `field(default_factory=list)`,
not a bare `keywords: list[str] = []`.** A bare mutable default on a
dataclass (or any Python class/function) is evaluated exactly once, at
class-definition time, and that *same* list object would then be
shared across every `LibraryEntry` instance that doesn't explicitly
pass its own `keywords=` -- mutating one entry's keyword list in place
(e.g. via `.append(...)`) would silently corrupt every other entry's
keywords too. `dataclasses.field(default_factory=list)` instead calls
`list()` fresh for each new instance, giving every `LibraryEntry` its
own independent list. `field`/`dataclasses` were already imported in
`library_catalog_service.py` (used for `LibraryRecord.entries` and
`LibraryCatalog.libraries`), so no new import was needed. Pinned
directly by
`test_fresh_library_entries_do_not_share_a_mutable_keywords_list`,
the single most important regression test in this slice.

### `_normalize_keywords(value) -> list[str]` helper

Mirrors `_optional_dict`'s/`_clamp_rating`'s/`_normalize_flag`'s
"coerce defensively, never raise on bad persisted data" pattern,
module-level in `library_catalog_service.py`:

```python
def _normalize_keywords(value) -> list[str]:
    if not isinstance(value, list):
        return []
    cleaned: list[str] = []
    seen: set[str] = set()
    for item in value:
        text = str(item).strip()
        if not text:
            continue
        key = text.lower()
        if key in seen:
            continue
        seen.add(key)
        cleaned.append(text)
    return cleaned
```

Behavior, all pinned by direct unit tests against `_normalize_keywords`
itself (not just through the dataclass/service layer):

- **Non-list input** (missing key, `None`, a stray `str`/`int`/`dict`)
  normalizes to `[]` rather than raising or attempting to iterate a
  non-iterable.
- **Each item is coerced to `str`** (defensive against a hand-edited
  catalog containing a stray non-string list item) **and `.strip()`-ed**
  (so `"  sunset  "` and `"sunset"` are treated identically).
- **Empty/whitespace-only entries are dropped** (`""`, `"   "`).
- **Case-insensitive dedup, first-seen casing preserved, order
  preserved.** `["Sunset", "sunset", "SUNSET", "Beach"]` normalizes to
  `["Sunset", "Beach"]` -- deduped by a lowercased key (so "Sunset"
  and "sunset" entered separately collapse to one entry, which is more
  user-friendly than treating them as two distinct keywords), while
  the *value* kept for that key is whichever casing/spelling was seen
  **first**, not a lowercased or otherwise rewritten version, and
  insertion order among the surviving keywords is preserved
  throughout.

`FilmstripView` does **not** keep its own local copy of this helper,
unlike `_clamp_rating`/`_normalize_flag`'s established per-file-copy
precedent (each of `library_catalog_service.py` and
`filmstrip_view.py` keeps its own small copy of those two). For
keywords, the UI side only ever needs a much simpler, display-oriented
coercion (see below) -- the view never needs the dedup/casing logic,
since that's purely a persistence-layer concern the catalog service
already owns, so a distinct, smaller `_normalize_keywords_for_display()`
was written in `filmstrip_view.py` instead of duplicating the full
service-side normalization.

### `FilmstripView._normalize_keywords_for_display(value) -> list[str]`

A small, local, display-only helper in `filmstrip_view.py`:

```python
def _normalize_keywords_for_display(value) -> list[str]:
    if not isinstance(value, list):
        return []
    return [str(item) for item in value if str(item).strip()]
```

This is intentionally *not* a full copy of the catalog service's
`_normalize_keywords` -- it only needs to turn a payload's possibly-
missing/malformed `"keywords"` value into something safe to join into
a tooltip string or pre-fill a dialog with. It does not dedupe or
reorder, because the final normalize/dedup happens catalog-service-
side when the edited list is actually persisted (see
`set_entry_keywords` below) -- duplicating that whole algorithm in the
view layer would be more code for no behavioral benefit, since
whatever the view displays gets re-normalized on the next
`entries_rebuilt` refresh anyway.

### `set_entry_keywords`'s no-op/dirty-save structure

Mirrors `set_entry_rating`/`set_entry_flag` exactly: look up the
entry via `_require_entry`, normalize the incoming value via
`_normalize_keywords`, return early (no `library.updated_at` bump, no
`_save_catalog()` call) if the normalized list equals the entry's
current `keywords` **by value**, otherwise mutate the entry, bump
`library.updated_at`, and save. The equality check is a plain `list`
`==` comparison, which Python already does element-by-element (not an
identity check), so `["sunset"] == ["sunset"]` correctly short-circuits
the no-op path even though they're different list objects.

### `UserRole` offset: `UserRole + 5`

`FilmstripView` already used `UserRole` (path), `UserRole + 1`
(status), `UserRole + 2` (favorite), `UserRole + 3` (rating), and
`UserRole + 4` (flag) -- confirmed by grepping every `UserRole` use in
`filmstrip_view.py` before picking a value, per the pick/reject-flags
slice's own precedent. Keywords are stored at **`UserRole + 5`** (a
`list[str]`), the next unused offset, set in `_apply_entry_payload()`
alongside the other four and read back in `_show_context_menu()` to
pre-fill the "Edit Keywords..." dialog with the item's current
keywords.

### Tooltip-only keyword display

In `_apply_entry_payload()`, the keywords line is appended to the
*same* prefix-building logic that already composes the favorite,
rating, and flag lines, after all three, without disturbing any of
them:

```python
prefix = ("Favorite\n" if favorite else "")
if rating > 0:
    prefix += f"Rating: {'★' * rating}{'☆' * (5 - rating)}\n"
if flag == "pick":
    prefix += "Pick\n"
elif flag == "reject":
    prefix += "Rejected\n"
if keywords:
    prefix += f"Keywords: {', '.join(keywords)}\n"
item.setToolTip(prefix + tooltip)
```

`item.setText(...)` is completely untouched -- it still only ever
reflects `favorite`. All four signals (favorite, rating, flag,
keywords) can appear in the same tooltip simultaneously, each on its
own line, in that fixed order, e.g.
`"Favorite\nRating: ★★★★★\nPick\nKeywords: sunset\n<name>"`. An empty
keyword list adds nothing to the tooltip (no empty `"Keywords: \n"`
line).

### Context menu: a fourth item, "Edit Keywords...", backed by `QInputDialog.getText`

`_show_context_menu()` was extended in place (not duplicated) with a
fourth menu item, added after the existing Favorite/Rating/Flag
sections: `"Edit Keywords..."`. Selecting it opens
`QInputDialog.getText(self, "Edit Keywords", "Comma-separated keywords:",
text=", ".join(current_keywords))`, pre-filled with the item's current
keywords (read off `UserRole + 5`, comma-and-space-joined). On accept
(`ok is True`), the returned text is split on commas, each piece is
`.strip()`-ed, empty pieces are dropped, and `keywords_changed` is
emitted with the path and the resulting list -- intentionally simple
UI-side parsing, since `set_entry_keywords`'s `_normalize_keywords`
does the final dedup/casing-preservation cleanup once the value is
actually persisted (see above). On cancel (`ok is False`), nothing is
emitted at all -- the dialog's returned text is discarded unread.

A submenu was not used, matching the Flag slice's decision for a small
number of options: one item needs no submenu at all.

### `LibraryController`/`MainWindow` wiring

`LibraryController.set_entry_keywords(file_path, keywords)` mirrors
`set_entry_favorite`/`set_entry_rating`/`set_entry_flag` exactly:
guard on `_current_library_id`/`file_path`, delegate to
`self._catalog_service.set_entry_keywords(self._current_library_id, file_path, keywords)`,
then `self._emit_libraries()` and
`self._rebuild_entries_for_current_library()` the same way. No new
aggregate (e.g. a `"keyword_count"`) was added to `_emit_libraries()`'s
per-library payload, for the same reason Ratings/Flags added none (see
Non-goals). `"keywords"` *was* added to both of `LibraryController`'s
per-entry payload dict literals (`_entry_payload()` and
`_on_thumbnail_ready()`), alongside their existing
`"favorite"`/`"rating"`/`"flag"` lines.

`MainWindow` adds one line, immediately below the existing flag
wiring:

```python
self._filmstrip_view.keywords_changed.connect(
    self._library_controller.set_entry_keywords
)
```

## 4. Contracts

- `LibraryEntry.keywords: list[str] = field(default_factory=list)` --
  new dataclass field, threaded through `to_dict()`/`from_dict()` via a
  new module-level `_normalize_keywords(value) -> list[str]` helper.
  **Not** a bare `= []` default (see Design above).
- `LibraryCatalogService.set_entry_keywords(self, library_id: str, path: str, keywords: list[str]) -> LibraryEntry`
  -- new method; normalizes `keywords` (strip/drop-empty/
  case-insensitive-dedup-preserving-first-casing/preserve-order); no-op
  (no save, no `updated_at` bump) if the normalized list equals the
  entry's current `keywords` by value.
- `LibraryController.set_entry_keywords(self, file_path: str, keywords: list[str]) -> None`
  -- new method; delegates to the catalog service against
  `self._current_library_id`, then refreshes views exactly like
  `set_entry_favorite`/`set_entry_rating`/`set_entry_flag`.
- `LibraryController._entry_payload()`/`_on_thumbnail_ready()` per-entry
  payload dicts both now include `"keywords": entry.keywords`.
- `FilmstripView.keywords_changed = pyqtSignal(str, list)` -- new
  signal (path, new keyword list), emitted by the context menu's
  "Edit Keywords..." action on dialog accept only.
- `FilmstripView` stores an item's keywords at
  `Qt.ItemDataRole.UserRole + 5` (a `list[str]`), alongside the
  existing `UserRole` (path), `UserRole + 1` (status), `UserRole + 2`
  (favorite), `UserRole + 3` (rating), `UserRole + 4` (flag).
- `MainWindow` connects `self._filmstrip_view.keywords_changed` to
  `self._library_controller.set_entry_keywords`.
- No existing method's signature or behavior changed. Favorite's,
  Rating's, and Flag's item text, tooltip prefixes, `UserRole` offsets,
  context-menu actions, and signals are all unmodified.

## 5. Nuances and failure modes

**Old catalog files predating this slice.** A catalog JSON file
written before this slice has no `"keywords"` key on any entry at
all. `LibraryEntry.from_dict()`'s
`payload.get("keywords", [])` already defaults to `[]` before
`_normalize_keywords` even runs (and `_normalize_keywords([])` returns
`[]` cleanly), so loading an old catalog produces entries with
`keywords == []` for every image, with no migration step and no
error. Pinned by
`test_keywords_missing_from_old_catalog_payload_defaults_to_empty_list`,
which also re-confirms `favorite`/`rating`/`flag` default correctly in
the same payload.

**Corrupt or garbage persisted values.** A hand-edited or corrupted
catalog file could contain `"keywords": "not-a-list"` or
`"keywords": {"a": 1}` -- any non-list type. `_normalize_keywords()`
coerces all of these to `[]` rather than raising or iterating
something that isn't iterable the way a list is -- pinned by
`test_normalize_keywords_rejects_non_list_input`.

**The mutable-default-factory bug, concretely.** If `LibraryEntry.keywords`
had instead been declared as `keywords: list[str] = []` (a bare
mutable default, not `field(default_factory=list)`), every
`LibraryEntry()` constructed without an explicit `keywords=` argument
would share the *exact same* underlying list object. Appending to one
entry's `.keywords` in place would then silently also appear on every
other entry's `.keywords` -- a classic, hard-to-notice Python footgun,
especially dangerous here since `LibraryCatalogService.list_entries()`
and friends construct many `LibraryEntry` instances over a session's
lifetime. `field(default_factory=list)` avoids this entirely by
calling `list()` fresh per instance. Pinned explicitly by
`test_fresh_library_entries_do_not_share_a_mutable_keywords_list`,
which constructs two separate `LibraryEntry()` instances, mutates one's
`keywords` in place via `.append(...)`, and asserts the other's list
is unaffected.

**Case-insensitive dedup can surprise a user who expects an exact
echo.** Entering `"Sunset, sunset"` in the Edit Keywords dialog and
re-opening it later shows only `"Sunset"` (the first-seen casing),
not both. This is a deliberate design choice (see Design above), not
a bug -- pinned by
`test_normalize_keywords_dedupes_case_insensitively_preserving_first_casing`.

**Favorite, rating, flag, and keywords coexisting in one tooltip.**
Explicitly tested: a favorited, 5-star, picked, "sunset"-keyworded
entry's tooltip is
`"Favorite\nRating: ★★★★★\nPick\nKeywords: sunset\n<name>"` -- all four
lines present, in that fixed order, none overwriting another.

**Favorite/Rating/Flag regression.** Every pre-existing Favorite,
Rating, and Flag test (catalog service, controller, and
filmstrip-view layers) was left completely unmodified and still
passes unchanged, confirming this slice's addition did not silently
alter any of the three.

**No multi-select to batch-apply keywords across.** Confirmed by
grepping `src/` for `SelectionMode`/`ExtendedSelection`/
`MultiSelection` before writing this note -- no match anywhere. The
filmstrip's `QListWidget` and the library grid both use Qt's default
single-selection mode. A future multi-select slice would need to
design batch-apply semantics for all four per-entry metadata fields
(favorite/rating/flag/keywords) together, not keywords alone, so it
was deliberately left out of this slice's non-goals rather than
half-built here.

## 7. Rollout

Purely additive: one new dataclass field (`LibraryEntry.keywords`,
default `[]` via `field(default_factory=list)`, so every existing
in-memory/freshly-loaded entry is unaffected), one new catalog-service
method, one new controller method, two new dict keys added to existing
payload literals, one new `FilmstripView` signal plus a context menu
extended with one more item (not replaced), and one new `MainWindow`
connect call. No existing method's signature changed. A plain revert
removes the feature entirely; any `"keywords"` keys already written to
a catalog file by this feature become inert, unread leftover JSON if
the feature is removed later (the same revert-safety story Flags,
Ratings, and "Import presets" documented before them).

`LibraryEntry` (`src/services/library_catalog_service.py`), threaded

`_entry_payload()`'s and `_on_thumbnail_ready()`'s payload dicts.

(`src/views/widgets/filmstrip_view.py`), imported `QInputDialog`, added
a local `_normalize_keywords_for_display()` display-only helper,
