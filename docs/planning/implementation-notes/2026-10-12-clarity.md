# Clarity adjustment

Related roadmap: Phase G / PDF section 16. Related workflow: `INCREMENTAL_WORKFLOW.md` sections 4 and 5.1.
Related prior slice: docs/planning/implementation-notes/2026-09-30-texture.md.

## 1. Problem, goal, and non-goals

Texture (medium-scale detail) is implemented, but PhotoEdit still has no
broad local/midtone-contrast control. This slice adds one neutral-by-default
Clarity control that enhances or softens local contrast using a much coarser
blur radius than Texture. It does not add Dehaze, Vignette, Grain,
sharpening, or noise reduction.

## 2. Current behavior

`ToolsPanel` emits flat basic adjustments; `ImageController` owns normalized
state and coordinates preview/final rendering; `ProcessingRequest` and
`ProcessingWorker` carry category dictionaries; `CombinedAdjustmentCommand`
provides the synchronous undo fallback. Texture is currently the final
pipeline stage, applied right after Color Grading.

## 3. Design and flow

Add a second -100..100 Clarity slider to the existing Effects section,
directly below Texture. Clarity remains a top-level persisted float for
consistency with other single-slider controls, while processing APIs carry
`{"clarity": value}` as a separate category, following Texture's pattern
exactly. The controller sends it through preview, final, synchronous,
restore, export, reset, and history paths. The worker applies it after
Texture and includes it in preview cache signatures. Pipeline order is now
... Color Grading -> Texture -> Clarity -> ... .

`ClarityProcessor` computes a Gaussian base (`sigma=20`, reflected borders),
forms the signed residual `source - base`, and adds up to 75% of that
residual. Positive values enhance the residual (more local contrast);
negative values move toward the coarse base (flatter midtones). It operates
per channel on float32 linear-light data and deliberately does not clip
intermediate values, preserving HDR headroom. Zero returns immediately.

The only functional difference from `TextureProcessor` is the blur sigma:
`20.0` instead of `2.0`. This 10x larger radius is what distinguishes
"local/midtone contrast" from Texture's "medium-scale detail" -- the same
design note that implemented Texture flagged this as a requirement for the
later Clarity slice (texture note section 6).

## 4. Contracts and compatibility

- State key: `clarity`, finite numeric float, default `0.0`.
- UI and processor range: `-100..100`; processor clamps out-of-range callers.
- Older payloads that omit the key restore as zero.
- No schema-version bump is needed because this is an additive defaulted key.
- No dependency is added; NumPy and existing OpenCV are sufficient.

## 5. Nuances and failure modes

Constant images must remain constant, neutral RGB must stay neutral, 1x1
images must not fail, and output shape/dtype must be retained. Reflect
borders avoid a dark artificial frame. Applying the same signed residual per
RGB channel avoids inventing color in neutral pixels. A test pins that
Clarity's sigma is strictly larger than Texture's, so a future refactor
cannot silently collapse the two effects back into the same scale. The
effect is intentionally an approximation, not a claim of Lightroom-identical
math.

## 6. UI/reskin, dependencies, and performance

The view contains only the slider and emits plain data; all math stays in
the processor. Existing throttling, cancellation, interactive proxies,
quality preview, and delayed full-resolution rendering remain unchanged.
Gaussian blur at a larger sigma is still linear-time (OpenCV's separable
implementation) and runs only off the UI thread during normal use; it costs
somewhat more than Texture's smaller-radius blur but was not observed to
be a bottleneck in the automated suite. Later Phase G slices (sharpening,
Dehaze, Vignette, Grain) must continue to use distinct scales/semantics from
both Texture and Clarity.

## 7. Test plan and manual smoke

Automated coverage pins identity/copy behavior, positive enhancement,
negative softening, constants/neutrals, dtype/shape/headroom, parameter
clamping, tiny images, the sigma-vs-Texture distinction, UI range/
emission/restore, queue and worker propagation/skip behavior, controller
persistence/export, and command undo -- mirroring Texture's test structure
file-for-file. Run the complete suite.

Manual: open a detailed image; move Clarity positive and negative; verify a
responsive preview, final render on release, undo/redo, reset, image-switch
restore, and export, with both Texture and Clarity active together.

## 8. Rollout, rollback, and acceptance

The feature is additive and identity-defaulted. A plain revert removes it;
older builds ignore the extra persisted key. Acceptance requires the full
vertical path, no UI-thread image math, backward-compatible restore, passing
targeted/full tests, clean diff checks, and honest manual-test reporting.

Plan approved -- implementation allowed: mirrors the approved Texture slice's
scope and wiring pattern (2026-10-12).

## 9. Implementation summary

Implemented `ClarityProcessor` (sigma=20.0, same residual/clamp/headroom
semantics as `TextureProcessor`) and wired it through every integration
point Texture touches: `ImageController` (defaults, processor/params state,
preview/final/sync rendering, export, restore/export state, reset,
`apply_adjustments`, the four `on_*_changed` debounced paths, slider-release,
`_has_pending_adjustment_changes`, delayed final render, and
`commit_adjustments`), `ProcessingRequest`/`ProcessingQueue`,
`ProcessingWorker` (processor, submit/apply/cache-key/signature,
perf logging), `CombinedAdjustmentCommand`'s synchronous fallback, and a
second "Clarity" slider in `ToolsPanel`'s Effects section below Texture.
Clarity is applied immediately after Texture everywhere in the pipeline.
No unrelated code was touched; the roadmap coverage table and git history
are left for the calling session.

Verification: complete suite **640 passed, 1 deselected in 106.09s**
(the pre-existing `test_geometry_is_restored_on_next_launch` offscreen flake
noted in the Texture note persists and was deselected, not fixed, per the
task instructions). A live GUI smoke test was not performed in this
non-interactive environment.
