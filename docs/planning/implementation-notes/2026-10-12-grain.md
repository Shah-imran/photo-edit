## 1. Problem, goal, and non-goals

Texture, Clarity, Dehaze, and Vignette are implemented, but PhotoEdit still
has no way to add synthetic film grain. This slice adds one
zero-by-default Grain control, completing the Effects group of Phase G
(Texture/Clarity/Dehaze/Vignette/Grain). Unlike every prior Phase G
control -- all of which are pure, deterministic functions of their input
pixels -- Grain is the first control that is inherently stochastic: it
adds noise. It does not add Lightroom's full grain sub-panel (Size/
Roughness/Frequency controls) -- only the single "Amount" strength
slider, matching how Texture/Clarity/Dehaze/Vignette each shipped as a
single slider; the sub-controls are deferred to a future slice if ever
requested. It also does not add sharpening or noise reduction -- those
remain the three Detail items of Phase G (Sharpening, Luminance NR, Color
NR), left for a future slice.

## 2. Current behavior

`ToolsPanel` emits flat basic adjustments; `ImageController` owns
normalized state and coordinates preview/final rendering;
`ProcessingRequest` and `ProcessingWorker` carry category dictionaries;
`CombinedAdjustmentCommand` provides the synchronous undo fallback.
Vignette is currently the final pipeline stage, applied right after
Dehaze (which runs right after Clarity, which runs right after Texture,
which runs right after Color Grading).

## 3. Design and flow

Add a fifth 0..100 Grain slider to the existing Effects section, directly
below Vignette. Grain remains a top-level persisted float for consistency
with other single-slider controls, while processing APIs carry
`{"grain": value}` as a separate category, following Texture/Clarity/
Dehaze/Vignette's wiring pattern exactly (`grain_processor`/
`_grain_params`/`grain_params`, by direct analogy to
`vignette_processor`/`_vignette_params`/`vignette_params`). The controller
sends it through preview, final, synchronous, restore, export, reset, and
history paths. The worker applies it after Vignette and includes it in
preview cache signatures. Pipeline order is now
... Color Grading -> Texture -> Clarity -> Dehaze -> Vignette -> Grain,
so grain sits on top of the final toned/vignetted image, the way real
film grain would.

`GrainProcessor` generates additive Gaussian noise whose standard
deviation is `(grain / 100.0) * 0.04` (a small amount in linear-light
space -- even grain=100 should look like heavy but still photographic
film grain, not broken sensor noise). To approximate real grain's spatial
correlation rather than harsh per-pixel static, the noise is generated at
roughly a third of the image's linear dimensions (`round(dim / 3)`,
floored at `1`) and upsampled back to full resolution with
`cv2.resize(..., interpolation=cv2.INTER_LINEAR)`, which blurs the
upsampled noise into soft correlated blobs. The same 2-D noise field is
broadcast across all three channels (`noise[..., np.newaxis]` added to
every channel identically), so grain reads as luminance texture rather
than colored confetti -- the same "neutral/no color cast" principle
Vignette's radial mask relies on (vignette note section 5), applied here
to a noise field instead of a deterministic mask. Grain is
one-directional (`0..100`, Lightroom "Amount" semantics -- there is no
"remove grain" direction), unlike Texture/Clarity/Dehaze/Vignette, which
are all bidirectional (`-100..100`). Zero returns immediately, skipping
RNG construction entirely. No clipping is applied, preserving headroom.

## 4. Contracts and compatibility

- State key: `grain`, finite numeric float, default `0.0`.
- UI and processor range: `0..100` (one-directional, unlike the other
  four Effects sliders); the processor clamps out-of-range callers
  (including negative values, which clamp to `0`, i.e. identity).
- Older payloads that omit the key restore as zero.
- No schema-version bump is needed because this is an additive defaulted
  key.
- `cv2` (already a dependency via Texture/Clarity/Dehaze) is reused for
  the upsample step; no new dependency is added.

## 5. Nuances and failure modes

**Determinism for caching and tests (the central design decision of this
slice).** `ProcessingWorker` caches preview results keyed by an
adjustment signature built from every category's params
(`_cache_key`/`_adjustment_signature`), and this codebase's idempotency
expectation throughout Phase G is that `process(image, params)` is a pure
function -- calling it twice with the same inputs must return the same
array. A naive `np.random.normal()` call (unseeded, drawing from NumPy's
global RNG state) would violate this three ways: (a) the preview cache
would miss on every single call, since the cached image would never
match a freshly-rendered one bit-for-bit even with identical params
(cache correctness does not strictly require this, since the cache keys
on params and shape rather than on the result, but it does mean every
"cache hit" would silently show a different grain pattern than what was
last rendered, which is confusing and makes the cache's `cache=hit` log
line a lie); (b) idempotency-style tests in this repo's existing pattern
(call `process()` twice, assert equal output) would fail outright, and
such a test is this slice's single most important regression guard
(`test_same_image_and_params_are_deterministic`); and (c) it would break
the general principle every other Phase G processor upholds, that the
pipeline is a pure function of `(image, all category params)` with no
hidden global state.

The fix is a **seeded** `numpy.random.default_rng`, seeded from a key
derived from the image's shape and the grain amount:
`hash((tuple(int(d) for d in shape), round(value, 4))) & 0xFFFFFFFF` (see
`GrainProcessor._seed_for`). Two properties make this adequate:

1. **Determinism.** Python's `hash()` of a tuple of `int`s and a `float`
   is deterministic *within a process* and is **not** subject to
   `PYTHONHASHSEED` randomization -- that randomization applies only to
   `str`/`bytes`/`datetime` hashing, never to `int`/`float`/tuples of
   them. So `hash((shape, value))` returns the same number every time
   this process calls it with the same `shape`/`value`, which is exactly
   the guarantee `process(same_image, grain=X)` called twice needs. (It
   is *not* guaranteed to be the same number across different Python
   *processes* -- e.g. between a test run and a later run, or between the
   main process and a worker process, if one existed -- because CPython's
   small-int/float hash is stable but combined-tuple hashing details can
   in principle differ across interpreter versions. This does not matter
   here: nothing in this codebase persists or compares a grain seed or a
   grain-noise field across process boundaries; only within-process reuse
   of the same `(shape, value)` pair needs to match, and it always does.)
2. **Non-determinism across different inputs.** Rounding `value` to 4
   decimal places before hashing means float jitter from upstream
   float32/float64 conversions cannot flip the seed for what is
   conceptually the same amount, while two genuinely different amounts
   (or two different image shapes) hash to different seeds with
   overwhelming probability, so `process(image, grain=X)` and
   `process(image, grain=Y)` (or the same amount on a differently-shaped
   image) produce visibly different noise, which several new tests pin
   directly (`test_different_grain_amount_changes_output`,
   `test_different_image_shape_changes_noise`).

This also means grain amount and image shape are the *only* two things
that can change the grain pattern -- the actual pixel *content* of the
image does not factor into the seed at all. This is a deliberate,
documented simplification: it keeps the seed formula simple and cheap
(no hashing of potentially large pixel buffers), and it is harmless for
this feature's purpose (grain is meant to look like photographic grain
texture, not to respond to image content), but it does mean two visually
different images of the same shape, with the same grain amount, get the
*same* noise field. This is invisible to the user in practice (the noise
is additive and small relative to image content) and is consistent with
how the other four Effects processors treat params as the only
cache-relevant input beyond the image's shape in several of their own
tests.

**Downsample/upsample and tiny images.** The low-res-then-upsample trick
divides the image's height/width by 3 and rounds, which is floored at `1`
(`max(1, round(dim / 3))`) so a 1x1, 2x2, or 3x3 image cannot produce a
zero-size intermediate array -- `cv2.resize` would raise on a zero
dimension. For a 1x1 image the "downsampled" noise array is already 1x1,
so the processor skips the `cv2.resize` call entirely when the computed
small size already equals the full size (an explicit shape-equality
check), both as a minor optimization and to avoid relying on
`cv2.resize`'s behavior when source and destination sizes are identical.

**No clipping, dtype/shape preserved.** Like Texture/Clarity/Dehaze/
Vignette, Grain does not clip its output, preserving HDR headroom for
later pipeline stages or export tone mapping. Output dtype (`float32`)
and shape are retained unconditionally.

**Zero is a true no-op, including for performance.** `grain == 0.0`
returns `source.copy()` immediately, before constructing an RNG or
computing a downsample size at all -- this both avoids any read of
`numpy.random.default_rng` module state on the (overwhelmingly common)
default/no-op path and means tests and callers that pass `grain=0.0`
never have to reason about seeding.

## 6. UI/reskin, dependencies, and performance

The view contains only the slider and emits plain data; all math stays in
the processor. Existing throttling, cancellation, interactive proxies,
quality preview, and delayed full-resolution rendering remain unchanged.
Generating noise at roughly 1/9th the pixel count of the full image
(1/3 linear in each dimension) and upsampling with a cheap bilinear
`cv2.resize` is fast relative to Texture/Clarity/Dehaze's Gaussian blurs
over the full-resolution image, and was not observed to be a bottleneck
in the automated suite. No new dependency is added (`cv2` is already a
Texture/Clarity/Dehaze dependency; `numpy.random.default_rng` is part of
NumPy's existing API surface). This completes the Effects group of Phase
G (Texture, Clarity, Dehaze, Vignette, Grain); the three Detail items
(Sharpening, Luminance NR, Color NR) remain deferred to a future slice,
as called out in section 1.

## 7. Test plan and manual smoke

Automated coverage pins identity/copy behavior at zero, **determinism**
(the same image and grain value processed twice produce byte-identical
output -- the single most important test in this slice), different grain
amounts producing different output, different image shapes producing
different noise, grain actually adding nonzero variance relative to the
source when `grain > 0`, dtype/shape/headroom preservation without
clipping, parameter clamping in both directions (negative clamps to zero/
identity; above 100 clamps to 100), 1x1 and other tiny/sub-downsample-
target images not crashing, and the same-noise-across-channels
(no-color-cast) property. Integration coverage mirrors
Texture/Clarity/Dehaze/Vignette's test structure file-for-file: queue
param threading, worker propagation/skip-at-zero behavior and cache-key
sensitivity to grain params, controller persistence/export/undo, command
undo, and UI range (`0..100`, not `-100..100`)/emission/restore. Run the
complete suite.

Manual: open an image; move Grain from 0 upward; verify a responsive
preview showing correlated grain texture (not harsh pixel static) rather
than a flat color shift, final render on release, undo/redo, reset,
image-switch restore, and export, with Texture, Clarity, Dehaze,
Vignette, and Grain active together.

## 8. Rollout, rollback, and acceptance

The feature is additive and identity-defaulted. A plain revert removes
it; older builds ignore the extra persisted key. Acceptance requires the
full vertical path, no UI-thread image math, backward-compatible restore,
passing targeted/full tests, clean diff checks, and honest manual-test
reporting.

Plan approved -- implementation allowed: mirrors the approved Texture/
Clarity/Dehaze/Vignette slices' scope and wiring pattern (2026-10-12).

## 9. Implementation summary

Implemented `GrainProcessor` (seeded, shape-and-amount-derived RNG for
determinism; low-res Gaussian noise upsampled with bilinear
interpolation for spatial correlation; same noise field broadcast across
channels; one-directional `0..100` range unlike the other four Effects
controls) and wired it through every integration point Vignette touches:
`ImageController` (defaults, processor/params state, preview/final/sync
rendering, export, restore/export state, reset, `apply_adjustments`, the
four `on_*_changed` debounced paths, slider-release,
`_has_pending_adjustment_changes`, delayed final render, and
`commit_adjustments`), `ProcessingRequest`/`ProcessingQueue`,
`ProcessingWorker` (processor, submit/apply/cache-key/signature, perf
logging), `CombinedAdjustmentCommand`'s synchronous fallback, and a fifth
"Grain" slider (`min_value=0.0`, unlike the other four sliders'
`min_value=-100.0`) in `ToolsPanel`'s Effects section below Vignette.
Grain is applied immediately after Vignette everywhere in the pipeline,
as the final Effects stage. No unrelated code was touched; the roadmap
coverage table and git history are left for the calling session.

As with each prior Effects slice, two existing exact-dict contract tests
in `test_image_controller.py`
(`test_get_adjustment_state_returns_normalized_defaults` and
`test_restore_adjustment_state_applies_saved_values`) asserted the
complete `get_adjustment_state()` payload key-for-key and needed a
`"grain": 0.0` entry added alongside the other now-14 top-level float
keys.

Verification: targeted new/changed tests (processor + controller +
command + queue + worker + tools-panel Grain tests, run alongside the
full Vignette/Dehaze/Clarity/Texture suites they extend) **208 passed**;
complete suite **696 passed, 1 deselected in 108.12s** (the pre-existing
`test_geometry_is_restored_on_next_launch` offscreen flake noted in the
Texture/Clarity/Dehaze/Vignette notes persists and was deselected, not
fixed, per the task instructions). A live GUI smoke test was not
performed in this non-interactive environment.
